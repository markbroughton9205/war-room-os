# War Room — Research/Data-Provider Infrastructure Inventory (ground truth, read from code)

Generated by direct code inspection. Supersedes any prior verbal counts ("23 adapters", "~35 live
endpoints") — those are not reflected anywhere in the actual codebase and should be discarded.

## 1. Architecture overview

There are **two distinct, non-overlapping systems** that touch "outside knowledge":

### A. `lib/research-engine/` — the structured, typed, extensible provider system

This is the system that matches the Earth Knowledge Registry's shape (per-provider category,
auth mode, capability, provenance). It is the correct target for Earth Knowledge integration work.

- `core/types.ts` — canonical `ResearchProviderId` union type (31 members), plus
  `ResearchProviderCategory`, `ResearchProviderCapability`, `ResearchQueryIntent`,
  `ResearchDocument`/`ResearchProvenance`/`ResearchCitation` (the normalized record + provenance
  shape every adapter must produce).
- `config/providerEnv.ts` — `RESEARCH_PROVIDER_ENV`: one descriptor per provider ID (31 entries,
  1:1 with the type union). Each descriptor declares `requiredEnv`/`optionalEnv`, `defaultBaseUrls`
  (also the SSRF allowlist source of truth), `implemented: boolean`, and free-text `notes` that are
  unusually precise about exactly which sub-endpoints/capabilities are and are not wired up.
- `providers/registry.ts` — `IMPLEMENTED_PROVIDER_ADAPTERS`: a `Partial<Record<ResearchProviderId,
  ResearchProviderAdapter>>` map. **This is the actual "can the router call this" source of truth.**
  Only providers with a real adapter file appear here (24 of the 31).
- `providers/*.ts` — one file per implemented adapter (24 files) + `adapter.ts` (shared adapter
  interface), `shared.ts` (shared fetch/parse helpers).
- `routing/router.ts` — `routeResearchQuery()`: intent → candidate-provider table
  (`INTENT_PROVIDER_MAP`, 20 `ResearchQueryIntent` values covering medicine, legal, government
  contracts, economics, climate, hazards, geospatial, historical, cultural, space, cyber threat
  intel, legal-entity, etc.), narrowed to providers that are both `configured` (env present) and
  `implemented` (adapter exists). Explicit `query.providers` overrides intent routing. This is
  already fully domain-aware routing — mission item 17 is largely already satisfied for the 24
  implemented providers.
- `security/` — `hostAllowlist.ts` (built from `defaultBaseUrls`), `providerGate.ts`,
  `targetUrlValidator.ts` (SSRF guard), `safeFetch.ts`, `redact.ts` (credential redaction in
  logs/errors), `xmlLite.ts` (XML parsing without an external XML lib).
- `diagnostics/validation.ts` (3,992 lines) — `runResearchEngineValidation()`: a single exported
  function, **purely deterministic** (zero `fetch()` calls, zero live network checks) covering
  types/config/routing/security invariants. Run via `pnpm run validate:research-engine`.
- `diagnostics/audit.ts` — safe (non-secret) provider status introspection.
- `normalization/dedupe.ts`, `citations/citations.ts`, `cache/ttlCache.ts` — shared normalization
  pipeline.

**Important gap**: there is no `validate:research-engine:live` script (compare to
`validate:public-rss:live`, `validate:income-loot:live`, `validate:settlement-intelligence:live`,
which do exist). No provider in `lib/research-engine/` has ever been proven by a reproducible live
HTTP call captured in this repo's validation harness. Per the mission's definitions, **all 24
"implemented" research-engine providers are `IMPLEMENTED_NOT_LIVE_VERIFIED`, not
`LIVE_IMPLEMENTED`**, until a live-probe harness is added and run.

### B. General web search/scrape tool layer (Tavily / Firecrawl / Grok / direct fetch) — NOT part of the ResearchProviderId system

This is a separate, older, more organically-grown layer used by opportunity discovery, income
scouts, Baby-AI chat, and the news/RSS fallback tier. It is **not** registered under
`ResearchProviderId` and the research-engine router cannot select it. Real `fetch()` calls to real
endpoints exist in many places, with meaningful duplication:

- `lib/tools/internet/registry.ts` + `types.ts` — `InternetToolId` registry: `tavily`, `firecrawl`,
  `grok_xai`, `direct_fetch`. Metadata only (name/envKey/notes), no fetch logic itself.
- `lib/providers/health.ts` — live health-check pings for xAI (`api.x.ai/v1/models`), Tavily
  (`api.tavily.com/search`), Firecrawl (`api.firecrawl.dev/v2/scrape`).
- `lib/internet/warRoomSearchProviders.ts`, `lib/internet/probes.ts` — another Tavily/Firecrawl/xAI
  fetch + probe implementation.
- `lib/income/tavily.ts`, `lib/income/firecrawl.ts` — income-scoped Tavily/Firecrawl clients.
- `lib/economic/scout/tavilyScout.ts`, `lib/economic/scout/firecrawlScout.ts` — economic-scout-scoped
  clients (again).
- `lib/signals/providers.ts`, `lib/signals/providers/firecrawlSearch.ts` — signals-scoped Tavily/
  Firecrawl clients (again).
- `lib/baby-ai/privateChatRoute.ts` — yet another direct Tavily/Firecrawl call site.
- `lib/ai/providers/xai.ts` — Grok/xAI as an LLM council provider (chat completions), distinct from
  Grok-as-a-search-tool.
- `lib/intelligence/sourceRegistry.ts`, `lib/intelligence/sources/retrievalOrchestrator.ts`,
  `lib/intelligence/sources/persistentSourceNetwork.ts`, `lib/intelligence/newsIntelWall.ts`,
  `lib/intelligence/queryPlanner.ts` — a separate "intelligence" source-orchestration layer, appears
  to be the backing for Council briefings / news intel, distinct again from research-engine.

**Reconciliation implication**: Tavily/Firecrawl/Grok/direct-fetch are real, live, credentialed,
general-purpose search/scrape tools — they satisfy `general_web` / `news` category needs broadly
but are not registry-source-specific (they can't be pointed at "Wikidata" specifically, etc.), and
they are duplicated across ~6 call sites rather than centralized. They should be treated as
existing, protected infrastructure (mission item 18) and NOT rebuilt, but also not double-counted
as Earth Knowledge Registry source coverage — Registry sources need dedicated, source-specific
adapters in the `lib/research-engine/providers/` pattern.

### C. RSS/NWS fallback tier — `lib/research/`

- `publicRssFeeds.ts` (237 lines) — hand-verified, live-tested RSS/RDF feed list (BBC, NASA,
  Bloomberg, TechCrunch, ABC, Al Jazeera, Le Monde, The Hindu, SCMP, SMH, AllAfrica, Deutsche Welle,
  etc.), explicitly documents dead/excluded feeds it tried and rejected (AP, Reuters, FT,
  weather.gov docs page). Real XML parsing, no external XML lib.
- `nwsAlerts.ts` (117 lines) — `api.weather.gov/alerts/active`, `application/geo+json`, real
  fetch+parse, state-name→abbreviation resolution for `?area=` filtering.
- `researchIntent.ts`, `researchRouter.ts`, `researchEvidence.ts` — intent classification and
  routing for this fallback tier, separate from `research-engine/routing/router.ts`.
- Has live validation: `validate:public-rss:live` (real network), plus deterministic
  `validate:public-rss` and `validate:nws-alerts`.
- This tier is explicitly a fallback used "when Tavily/Grok are unavailable or unauthenticated" —
  already live-verified, already protected, do not modify without a documented reason.

### D. `lib/earth-intelligence/` — NASA GIBS tiling, pre-existing

- `gibsLayers.ts`, `gibsServerConfig.ts`, `gibsTileUrl.ts`, `validation.ts` — curated NASA GIBS WMTS
  layer catalog + tile URL builder. The research-engine `nasa_gibs` adapter wraps this rather than
  duplicating it (confirmed via providerEnv.ts note). Has its own
  `validate:earth-intelligence` script.

## 3. Provider-ID references found outside the registry

Grepped the full repo for provider-ID-shaped strings; no `ResearchProviderId` value is referenced
or implemented anywhere outside `lib/research-engine/`. `sam_gov` also has a second, unrelated
SAM.gov integration under `lib/opportunity-agents/sources` (revenue/opportunity-discovery scoped,
explicitly noted as distinct in providerEnv.ts) — not a duplicate Earth Knowledge source, a
different subsystem entirely.

## 5. Validation scripts relevant to this domain (from package.json)

```
validate:research-engine        — deterministic, lib/research-engine/diagnostics/validation.ts (no live calls)
validate:research-intent        — deterministic, lib/research/researchIntent.validation.ts
validate:public-rss             — deterministic, lib/research/publicRssFeeds.validation.ts
```

No `validate:research-engine:live` script exists — this is the single biggest structural gap
between "implemented" and "live verified" for the 24 real research-engine adapters.

## 6. No pre-existing machine-readable Earth-Knowledge-Registry-shaped completion file

Nothing in the repo currently tracks registry-source-level reconciliation state (`LIVE_IMPLEMENTED`
/ `MISSING` / etc. per Earth Knowledge Registry entry). `config/providerEnv.ts` is the closest
existing analog (per-*War-Room-provider* config status) but it is scoped to War Room's own 31
provider IDs, not to the full external registry of hundreds of named sources. A new file will need
to be created to track registry-source-to-provider-ID mapping and the fuller state taxonomy the
mission requires.
