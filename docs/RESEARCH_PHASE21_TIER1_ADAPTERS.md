# Phase 21 Tier 1 Research Engine adapters

## MITRE ATT&CK — IMPLEMENTED / REAL + FUNCTIONAL

**HISTORICAL VALIDATION STATE**: PARTIAL — reachable and structurally correct, but exact ATT&CK-ID lookups were unreliable due to the pagination/ranking defect described below. This was the adapter's status before the pagination/exact-ID repair.

**CURRENT VERIFIED STATE**: REAL + FUNCTIONAL — the pagination/exact-ID/ranking repair below is complete, and exact-ID lookups have been independently re-validated live (5/5 consecutive passing runs; see the repair and re-validation paragraphs below for detail). This is the adapter's current status.

**Independent validation (Claude, 2026-08-13) found the adapter as originally delivered was pointed at the wrong TAXII service entirely**, not merely blocked by network reachability as first claimed. MITRE migrated TAXII 2.1 clients to `https://attack-taxii.mitre.org` (API root `/api/v21/`) as of ATT&CK v15 (April 2024); the legacy `https://cti-taxii.mitre.org/taxii/` host is TAXII 2.0 only. The original code pointed at `cti-taxii.mitre.org/taxii/api/v21` (a host/path combination that matches neither the legacy 2.0 root nor the current 2.1 root), used the TAXII 2.1 Enterprise collection's bare legacy-2.0 UUID (`95ecc380-afe9-11e4-9b6c-751b66dd541e`) instead of the current TAXII 2.1 collection ID (`x-mitre-collection--1f5f1533-f617-4ca8-9ab4-6a02367fa019`), and sent a non-standard media type (`application/vnd.oasis.taxii+json;version=2.1` instead of the documented `application/taxii+json;version=2.1`). Separately, `externalId()` matched STIX `external_references[].source_name` against `'mitre attack'` (space) when the real field value is `'mitre-attack'` (hyphen), so `attack_external_id` never populated on any object regardless of connectivity.

All four defects were corrected in `lib/research-engine/providers/mitreAttack.ts`, `lib/research-engine/config/providerEnv.ts`, and `lib/research-engine/security/hostAllowlist.ts`. After correction, a live run against the real, current `attack-taxii.mitre.org` service returns HTTP 200 and normalizes real STIX 2.1 objects with correct IDs, external references, canonical URLs, and provenance — the request/response/normalization pipeline is REAL.

**The previously open pagination/exact-ID/ranking correctness defect has now been repaired and independently re-validated live.** Original defect: `run()` fetched only the first 500 objects of a given STIX type per query (no use of the TAXII `more`/`next` pagination cursor), while Enterprise ATT&CK currently has 858 `attack-pattern` objects — under half fit in one page. Local matching was unranked substring search across name/description/aliases/external ID with no prioritization for an exact ATT&CK-ID match, so a query for the exact ID `T1059` returned zero instances of T1059 among the top results — instead returning unrelated techniques whose descriptions happened to cite "T1059" in passing.

Repair, in `lib/research-engine/providers/mitreAttack.ts`:
- **Type routing now recognizes ATT&CK ID prefixes directly** (`T####[.###]` → attack-pattern, `G####` → intrusion-set, `S####` → malware/tool, `M####` → course-of-action) instead of relying solely on phrase keywords in the query text, so an ID like `G0007` no longer silently searches the wrong STIX type.
- **Ranked local matching** (`matchRank()`) replaces unranked substring search: exact ATT&CK-ID match outranks exact name, which outranks alias/name-prefix/name-substring matches, which outrank an ID or description merely containing the search term. Results are sorted by rank before truncating to the requested count.
- **Pagination was investigated and a live server-side defect was found in the process**: fetching the full `attack-pattern` type via the TAXII `next` cursor across two pages returned 30–40% of the *same* objects on page two as page one (confirmed by STIX id) rather than a clean continuation — a real instability in `attack-taxii.mitre.org`'s cursor, not a client-side bug — which meant some multi-page fetches silently dropped objects (including, in one reproduced case, the exact object being searched for) even though the server reported `more: false`. Fix: request a single page with a `limit` (2000) large enough to cover the full current corpus in one request with no cursor involved; confirmed live and repeatable across multiple trials that this returns all 858 `attack-pattern` objects with zero gaps or duplicates. The multi-page loop (`MAX_PAGES = 2`) remains as a defensive fallback for future corpus growth beyond one page, with the caveat that the cursor-overlap risk documented above would reapply if a second page is ever actually needed.

Live re-validation (2026-08-13, `pnpm run validate:phase21-tier1-live`) passed 5/5 consecutive runs after the fix (it was flaky — intermittently failing — before the single-page fix, confirming the cursor-overlap diagnosis). Additional live spot-checks confirmed correct exact-ID resolution across all four supported ID prefixes: `T1059` → "Command and Scripting Interpreter", `T1059.001` → "PowerShell", `G0007` → "APT28", `S0002` → "Mimikatz", `M1049` → "Antivirus/Antimalware"; free-text search (`phishing` → "Phishing", `T1566`) also confirmed correct. Full regression: `pnpm exec tsc --noEmit` clean, `pnpm run validate:research-engine` 491/491 PASS (no regressions in any other provider), `pnpm run build` clean.

**LIMITATION (known, pre-existing, not a blocker)**: free-text queries that embed the phrase-classifier keyword itself (e.g. `"APT29 group"`, where `"group"` selects the intrusion-set type) are matched as one literal substring against object fields, so they don't match unless that exact phrase appears verbatim in the object's name/description/aliases. A bare entity name without a type keyword (e.g. `"APT29"` alone) also defaults to the technique type rather than being tried against all types. This substring-only phrase-matching behavior is unchanged from the original implementation, predates this repair, and was not part of the reproduced/reported defect (which was specifically about exact-ID lookups) — it does not affect any explicitly claimed capability (search, ID-based lookup) and is noted here for completeness, not as an open blocker.

The MITRE ATT&CK TAXII 2.1 API also enforces a documented rate limit of 10 requests/10 minutes per source IP; repeated adapter/validation runs in a short window can produce slow or aborted responses that are not a defect in the adapter itself. The single-page-fetch fix above also reduces steady-state request volume relative to the old multi-page approach.

Implemented modes: technique (default) search/ID filtering, intrusion-set/group search, malware search, tool/software search, and mitigation search. It preserves STIX ID, ATT&CK external ID, name, text, type, timestamps, aliases, reference URL, and retrieval provenance. It is structured threat-knowledge/reference data, not live threat telemetry. MITRE ATT&CK content is attributed to MITRE and exposed under CC BY 4.0.

Live validation date: 2026-08-13. Real HTTP 200 responses, real STIX normalization, and correct exact-ID resolution were independently obtained against `attack-taxii.mitre.org` after the host/collection/media-type/matching/pagination repairs above. Classification: **REAL + FUNCTIONAL**.

## GLEIF LEI API — IMPLEMENTED / REAL + FUNCTIONAL

The adapter uses GLEIF's official public JSON:API v1 service at `https://api.gleif.org/api/v1`. It sends `Accept: application/vnd.api+json`; no authentication or API key is required. Exact 20-character LEI requests use `/lei-records/{lei}`. Other requests use the documented `filter[entity.legalName]` with bounded JSON:API `page[size]`/`page[number]` pagination. GLEIF documents 60 requests/minute/user and makes relationship URLs available in record links; this adapter preserves those links but does not crawl them.

It preserves LEI, legal name, entity and registration status, jurisdiction, address geography, managing LOU, BIC when supplied, relationship links, canonical self link, and provenance. GLEIF LEI data is subject to the GLEIF LEI Data Terms of Use. Live validation independently repeated on 2026-08-13 received and normalized real records from the official service, both by exact LEI (`529900T8BM49AURSDO55`) and by legal-name filter (`Deutsche Bank`, 382 total matches, page-1 fields matching the adapter's field-path assumptions exactly).

**Independent TypeScript audit found 7 real `tsc --noEmit` errors (TS18048, "entity is possibly undefined")** in `normalize()`, all stemming from a guard clause that checked a derived `name` variable but not `entity` itself, so TypeScript could not narrow `entity` for later property access. This was a genuine compile-time defect distinct from the adapter's live runtime behavior. Fixed by adding `!entity` to the existing early-return guard. `pnpm exec tsc --noEmit` and `pnpm run build` are both clean after the fix.
